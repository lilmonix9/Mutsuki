# 多尺度体素世界创作平台 · 项目书 Draft 0.4

Nov 25, 2026

本版（0.4）在 0.3 的基础上并入了产品负责人的补充意见：**AI 自主推进、全云端 GitHub 工作流、轻量化与画质分级**，并把精确建造和基础数据保护提前到 MVP。核心架构一节改为区分「锁定的产品要求」和「可调整的技术方案」。

读者有两类：产品负责人（许愿者，负责方向、重大决策与成品体验），以及执行开发的 AI（负责方案、编码、测试）。两者冲突时，以本书和仓库内的决策记录为准，而不是某一次对话里的说法。

优先级约定沿用 0.2：**核心**＝第一批自用能力；**后期**＝核心稳定后的扩展；**愿景**＝长期方向，不代表已承诺。

## 1. 定位与愿景

一款离线优先、以体素为基础、兼容其他几何表示的三维世界创作软件，只专注于创造本身。用户可以在同一个世界里雕刻山脉、建造建筑、布置室内、制作精细物件，并把原创故事与地点关联起来。

理想形态：Minecraft 的建造自由度，Blender 的部分建模与视觉表现，现代引擎的场景规模，远低于专业软件的操作门槛。

设计哲学：尽可能少的底层规则，尽可能多的创作可能。底层不强求统一数据结构，上层必须提供统一的选择、编辑、组织和保存体验。

差异化：**空间化世界观档案**。三维编辑器很多，文字世界观工具也有，但能把角色、历史、剧情直接挂在可漫游空间上的软件几乎没有。它在路线上属于后期，但其地基（永久对象 ID）属于核心，从第一天就要有。

## 2. 开发模式：AI 开发，人类许愿

代码、构建、测试和发布全部由 AI 在云端完成。产品负责人不配置环境、不编译、不检查实现，只在软件形成较完整的可用版本后集中体验和反馈。

| 角色 | 负责 |
| --- | --- |
| 产品负责人（人类） | 提出需求与方向；重大决策拍板；成品体验与集中反馈 |
| 开发 AI | 技术选型、开发、构建、测试、发布、维护项目记忆；如实记录无法自动验证的问题 |

**需要产品负责人拍板的只有三类**：重大产品方向变更；核心需求删减；不可逆的数据架构变更（如存档格式的不兼容改动）。其余技术决策由 AI 自主做出，并写入决策记录，供事后查阅。

**云端工作流**

- GitHub 是代码仓库，也是项目记忆的载体；不同 AI 依据仓库文档接续开发。
- GitHub Actions 自动构建与测试，产出 Windows 与 Linux 的便携版或安装包。
- 阶段性版本通过 GitHub Releases 发布；历史可运行版本全部保留，可回退。
- 关键依赖固定版本，构建可复现；保留构建日志、测试结果与性能记录。
- 普通云端构建机没有独立显卡。渲染相关测试须使用软件渲染（如 Mesa 的 llvmpipe 或 lavapipe），只能证明「画得出、画得对」，不能证明真实显卡上的表现。

**AI 的已知弱点与对策**

| 弱点 | 后果 | 对策 |
| --- | --- | --- |
| 跨会话失忆 | 后期推翻早期设计，重复踩坑 | 仓库内项目记忆，每次开工先读（第 7 节） |
| 看不见画面 | 误以为接缝、闪烁已修好 | 几何检查＋软件渲染固定机位截图比对；仍无法确认的写入待体验清单 |
| 容易宣称完成 | 用演示或未接线 UI 冒充功能 | 完成以云端测试和可下载构建为准；禁止降低标准制造通过（第 6 节） |
| 喜欢多做一点 | 范围蔓延，核心迟迟不稳 | 一次只做一个任务；范围外的想法记入待议清单 |
| 长期无人纠偏 | 方向跑偏，到成品体验时才发现 | 每次 Release 附一页大白话更新说明和几张截图；产品负责人可随时看一眼，但不作为继续开发的前提 |

## 3. 核心要求与当前技术方案

这一节区分两类内容。**产品要求**是锁定的，改动须由产品负责人拍板。**技术方案**是当前的最佳判断，AI 可以根据实验结果调整，但须写入决策记录。

**产品要求（锁定）**

| 要求 | 含义 |
| --- | --- |
| 多尺度编辑 | 同一世界里，从地理尺度到毫米级细节都能编辑；地形可按区域细化，物件可有各自的精度 |
| 物件即小世界 | 每个物件有自己的坐标系与精度，可以进入局部编辑 |
| 非破坏性变换 | 移动、旋转、缩放不改写原始几何；只有用户明确要求时才重采样 |
| 平滑与硬边共存 | 自然地形连续平滑，建筑墙角保持锐利；换颜色不重建几何 |
| 永久对象 ID | 移动、改名、重组时不变；复制生成新 ID；删除后不回收 |
| 一切皆操作 | 所有持久编辑都可撤销、可记录、可由脚本复现；UI 不绕过这一层 |
| 独立开放的存档格式 | 不依赖引擎，有版本号和公开文档；生成器版本、参数、种子随档保存，旧存档不错位 |
| 画质与数据解耦 | 世界范围、编辑精度、几何分辨率、渲染 LOD、画质五者互相独立；降低画质不降低模型精度，也不限制可建内容 |
| 大世界坐标稳定 | 远离原点时，编辑和拾取不抖动、不偏移 |

**当前技术方案（可调整）**

| 领域 | 当前方案 |
| --- | --- |
| 引擎 | 首选 Godot 4 + Voxel Tools，备选 Bevy + Rust；不自研渲染器 |
| 地形 | 分块密度场，Transvoxel 或同类过渡网格 |
| 建筑与物件 | 稀疏体素网格，必要时辅以普通网格 |
| 精度档位 | 相邻档位 4 倍，对应八叉树两层 |
| 坐标 | 局部整数网格＋分块全局坐标或双精度；相机相对渲染或浮动原点 |
| 命令层 | 结构化命令＋事务＋逆向数据，配合分块快照与检查点 |
| 渲染缓存 | 网格与 LOD 均为可重建的缓存，不进入存档 |

## 4. 北极星场景

**一座浮空山岛上的一间书房。** 每个功能都要回答：它能帮我完成这个场景吗？不能就延后。

1. 从虚空模板开始，雕刻约 1 km 宽、300 m 高的山岛。
2. 在山上建一间约 8×6×3 m 的书房，墙体为硬边。
3. 在桌上放一只约 10 cm 高的茶杯（约 3.9 mm 局部精度）。
4. 从远景飞入室内，山体平滑、墙角锐利、茶杯精细，全程无裂缝。
5. 进入茶杯局部编辑，改一处细节；复制一个并放大三倍，原杯不受影响。
6. 保存、关闭、重开，结果与关闭前一致；再用第一人称走一遍。

开发期间，AI 用脚本按同样的步骤自动复现这个场景，作为回归测试；成品体验时，由产品负责人在编辑器里亲手做一遍。另设一项坐标压力测试：在距原点约 1000 km 处重复步骤 2–5，检查抖动与拾取精度。

## 5. 阶段路线

阶段严格按顺序推进，是否过关以自动化测试为准，不以人工验收为前提。与 0.3 相比有两处变化：**P0 改为云端基础加可抛弃的技术实验**，风险验证前置；**正式核心系统在 P1 依据实验结论重新搭建**。

1. **P0 · 云端基础与技术实验**
   - 云端基础：GitHub 仓库、Actions 流水线、Windows 与 Linux 构建产物、软件渲染测试环境、项目记忆文件。
   - 可抛弃的实验（代码不必遵循正式架构，也不默认进入正式产品）：多精度体素的真实编辑与存储；不同精度区域的衔接；平滑地形与硬边建筑共存；物件局部坐标与非破坏性变换；大世界坐标精度；大型地形的内存与渲染成本。
   - 重点确认：Voxel Tools 提供的渲染 LOD 是否等同于本项目需要的多分辨率编辑与存储；如果不等同，要自建哪一部分。
   - 过关：云端自动产出可直接运行的便携版；每项实验都有结论、数据和决策记录；完成选型。
2. **P1 · 正式核心**
   - 依据 P0 的结论，重新搭建命令层、独立存储格式、坐标体系、混合几何与接缝处理。
   - 过关：自动测试覆盖「编辑 → 撤销 → 重做 → 保存 → 重载」结果一致；接缝几何检查通过；1000 km 外误差在阈值内；基准场景达到核显性能目标。
3. **P2 · MVP（第一个体验版）**
   - 基础内容：新建、打开、保存；虚空、平原、简化海洋；地形笔刷与体素放置；物件创建、变换与局部编辑；撤销重做；基础颜色与光照；飞行与第一人称；最小 UI。
   - 精确建造：尺寸与坐标数值输入、网格吸附、角度吸附、轴向锁定、区域填充、基础尺寸测量。
   - 数据保护：自动保存、历史备份、原子化写入、完整性检测、保存失败时保留上一份有效存档。
   - 画质：极简与标准两档，视距与渲染距离可调。
   - 过关：自动化复现北极星场景通过，发布 Release，交产品负责人集中体验。
4. **P3 · 后期**：世界观注释（优先）、全局素材库与实例覆盖、建筑工具、显式烘焙、路径工具、植被渲染、PBR 材质、高质量阴影、水面反射、高画质与摄影档、外部模型导入、完整崩溃恢复、脚本 SDK。
5. **P4 · 愿景**：实时全局光照、体积云与体积雾、光线追踪、天气四季、侵蚀、高级流体、行星级地形、AI 创作接口、插件生态。

## 6. 性能、画质与验收

轻量化优先：以普通个人电脑和集成显卡能流畅运行为优化方向，Minecraft 的基础建造体验作为性能参考。创作自由度优先于画质，数据安全优先于功能数量。最低硬件要求须通过实测确定。

**画质档位**（所有档位共用同一份世界数据）

| 档位 | 定位 | 优先级 |
| --- | --- | --- |
| 极简 | 低性能设备、大规模场景编辑 | 核心 |
| 标准 | 日常建造与漫游 | 核心 |
| 高画质 | 高质量场景欣赏 | 后期 |
| 摄影 | 画面优先，可以不追求实时帧率 | 后期 |

视距、渲染距离、阴影、抗锯齿、植被密度、水面效果可以单独调节。高级视觉功能一律为可选项，不得成为运行依赖。

**大世界性能策略**：稀疏存储、分块加载与卸载、自适应编辑精度、多级渲染 LOD、视锥剔除与必要的遮挡剔除、隐藏面消除与网格简化、局部网格重建、异步后台处理、素材实例化与批量渲染、内存预算与缓存管理、程序化生成与增量存储。世界变大不得导致全部数据同时进入内存或显存；同时关注 CPU、内存、显存、磁盘空间和编辑延迟。

**性能目标**（初始值，待实测校准）

| 指标 | 目标 |
| --- | --- |
| 核显、标准档、北极星场景漫游 | ≥ 30 FPS |
| 笔刷反馈延迟 | < 100 ms |
| 持续记录 | 帧时间、峰值内存与显存、网格重建延迟、存档大小、重载时间 |

**验收方式**

| 问题 | 自动检测方式 |
| --- | --- |
| 地形接缝、裂缝 | 检查分块与精度边界处的网格是否闭合 |
| 远坐标抖动、点偏 | 多个距离下比较拾取点与期望点 |
| 变换后源数据变了 | 变换前后对源体素做哈希比对 |
| 存档后不一致 | 保存重载后的整世界哈希比对；模拟中途写入失败，确认旧存档完好 |
| 画面异常 | 软件渲染固定机位截图，与基准图比对 |

- 无法自动验证的视觉与交互问题，如实写入待体验清单，在成品体验时集中验证。
- 云端构建与测试通过，不等于所有目标硬件都兼容；真实显卡上的表现以成品体验和后续反馈为准。
- 测试可以随正常开发修改；禁止通过降低验收标准、删除失败测试或绕过真实功能来制造通过，禁止用截图、静态演示、硬编码场景或未接线 UI 冒充功能。

## 7. AI 项目记忆

GitHub 仓库就是 AI 的记忆。任何 AI 读完以下文件，都应能接着上一次继续工作。文档只求简明、准确、及时，不为流程写文档，不重复记录。

| 文件 | 内容 | 更新时机 |
| --- | --- | --- |
| `AGENTS.md` | 守则、产品要求、禁止事项、构建与测试命令、文档索引 | 产品要求部分须产品负责人拍板，其余 AI 可更新 |
| `docs/vision.md` | 本项目书 | 版本升级时 |
| `docs/decisions/` | 决策记录：选了什么、为什么、放弃了什么，每篇几行即可 | 重要决策后新增，不改旧篇 |
| `docs/progress.md` | 当前阶段、已完成、进行中、已知问题 | 每次会话结束前 |
| `docs/to-experience.md` | 无法自动验证、留待成品体验的问题 | 发现时追加 |
| `docs/backlog.md` | 范围外的想法与待议事项 | 随时追加 |
| `docs/format/` | 存档格式规范（即公开文档） | 格式变更时，同步版本号 |

**每次会话的工作流程**

1. 读 `AGENTS.md` 与 `docs/progress.md`，必要时读相关决策记录。
2. 一次只做一个任务，开始前写明完成标准。
3. 小步提交；云端测试全部通过才合并。
4. 更新 `docs/progress.md`；有重要决策则写决策记录。
5. 只有遇到第 2 t节的三类重大决策时，才停下来请产品负责人拍板。

## 8. 边界与开放问题

**不做**：生存、战斗、资源采集与合成、多人在线、完整游戏引擎、强制联网或付费依赖、复杂 NPC、角色动画、大规模实时物理。目标平台为 Windows 与 Linux 桌面端。

**待确认**

- [ ] 产品负责人电脑的配置（作为最低配置参考，不作为开发环境）。
- [ ] 执行开发的 AI 工具，及其在 GitHub 上的权限（写入仓库、运行 Actions、发布 Releases）。
- [ ] 仓库名称与可见性（私有或公开）。
- [ ] Voxel Tools 与 Godot 双精度编译能否同时启用（P0 实验）。
- [ ] 项目名称。

让想象拥有空间，让故事中的世界能够被创造、保存和亲自探索。
