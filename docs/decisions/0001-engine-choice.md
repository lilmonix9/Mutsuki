# 0001 · 引擎：首选 Godot 4 + Voxel Tools，备选 Bevy + Rust

- 日期：2026-11-25
- 状态：**暂定**，须由 P0 实验确认或推翻

## 选了什么

首选 Godot 4 + Zylann 的 Voxel Tools（godot_voxel）。备选 Bevy + Rust。不自研渲染器。

## 为什么

- **现成的体素能力**：Voxel Tools 已有分块体素存储、Transvoxel 平滑地形与 LOD、方块网格、多线程网格生成、流式加载，和项目书第 3 节的地形方案直接对口，能省下最贵的一段工作。
- **编辑器与 UI 现成**：Godot 自带成熟的 UI 系统、输入、场景树和导出管线；MVP 需要的最小 UI、飞行与第一人称都容易做。
- **轻量**：引擎本体小，有 Vulkan 与 OpenGL（兼容）两套渲染后端，符合「核显流畅」的方向。
- **导出简单**：官方模板可从 Linux 一次导出 Windows 和 Linux 版，适合全云端构建。
- **大世界**：Godot 支持双精度编译（`precision=double`），Voxel Tools 的 CI 也在构建 Float64 版本，有希望满足「大世界坐标稳定」。
- **开源（MIT）**，不依赖付费或联网。

## 放弃了什么 / 备选为什么是 Bevy

- Bevy + Rust：数据导向、性能可控、内存安全，适合自建存储层；但体素和编辑器生态要自己搭得更多，UI 薄弱，API 仍在频繁变动。若 P0 证明 Voxel Tools 的核心模型不合用、大部分都要自建，Bevy 的劣势就不大了，届时重新比较。
- Unity / Unreal：闭源或授权条款不稳，体量重，与轻量化和开放格式的目标不符。
- 自研渲染器：项目书明确不做。

## 已知风险（P0 要验证的）

1. **核心风险**：Voxel Tools 的 LOD 是「渲染 LOD」，不一定等同于本项目要的「多分辨率编辑与存储」（不同区域、不同物件各有精度）。如果不等同，要弄清自建哪一部分。
2. Voxel Tools 的完整功能以 C++ 模块形式提供，需要自己编译 Godot 编辑器和导出模板；也有 GDExtension 版，但功能可能有差别。要选定一种接入方式。
3. 双精度编译与 Voxel Tools 能否同时启用（项目书第 8 节待确认项）。
4. 存档格式必须独立于引擎：Voxel Tools 自带的存储格式只能作为参考或缓存，不能直接当存档。

## 什么时候重新评估

P0 每项实验结束后对照上面的风险；P0 结束时写一篇新的决策记录，给出最终选型。
